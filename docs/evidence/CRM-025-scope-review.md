## 范围缺陷及共同安全修复

`lib/ai/runtime/workbench-target-scope.ts` 原先只核对参数里显式出现的对象 ID。`crm_list_leads` 使用漏斗筛选，参数没有所选商机 ID，因此经过检查后仍列出同组织其他商机。`lib/ai/runtime/tools.ts` 是实际 handler 调用前的执行边界；仅在挂载时移除工具不足以防直接调用。

最小修复在工具挂载及执行边界共用范围规则：选定工作台对象时拒绝 `crm_list_leads`、`crm_list_conversations`、`crm_search_contacts`。这些现有 handler 无法把完整响应限定在所选对象，尤其会话列表在组织级分页后才过滤联系人。精确对象读取仍保留，普通无 scope 的列表仍沿用原组织、角色和漏斗权限。

独立审查同时确认了相邻的跟进读取缺口：`lib/followup/retorno-crm.ts` 允许根据联系人解析活跃商机，也允许明确商机不存在时回退联系人。`crm_list_followups` 现先检查调用者显式 ID，再在有选定商机时绑定该商机并移除联系人回退参数；商机消失时返回未找到，不能换查另一商机。仅选联系人或普通无 scope 的客户级跟进查询保持原语义。

修复不改知识检索、模型、提示词、评分、业务样例、SQL schema 或依赖。相对原产品 `2d5d411` 的产品差异限定在上述执行保护及其直接测试；知识适配器路径不变。恢复时仍须核对资料和权限语义一致，才能复用原 69 条 Wiki 探针。

## 接续决定及验收口径

原四根继续绑定旧基线 B0。共同安全修复版本 S 用于剩余 44 槽；后续通用质量修复候选 C 包含同一安全保护。D01/D02 的 B0→C 只做诊断，其他 22 场景作 S→C 主对照，H10 权限单列后最多 21 场景有模型答案配对。候选自身的单 Agent/三专家比较仍使用各有效同题配对，不能混淆两类分母。

H10 保持普通销售角色，原计划四个 POST 槽按现有 `permission_blocked` 分支记录真实 403、无 Run、业务不变，不升权、不拿 GET 预检替代 POST。旧四槽及这些拒绝槽均占 96 个计划槽，累计用量不重置。

现有脚本的产品版本锁、已用槽重新冻结、历史 `safe=false` 累计阻塞、单一 freeze 封存和旧密钥绑定都会挡住恢复，不能只修改 STATUS 后原样启动。动手 Agent 按 [STATUS 的具体接续要求](../STATUS.md#规划核验后的接续决定处理阻塞不反复受限交接) 修改已有脚本，追加任务/探针分段映射与恢复预检。保留历史失败及其原字节，仅允许受审查事故解除对后续槽的阻塞。

完成必要修复、直接验证和独立审查后自动继续；普通答错、缺证、partial 或预期拒绝结算该题后继续。一般审查或阶段结束不再拆环境。基线余槽、唯一候选、原计划复测、独立汇总完成后再清理并交最终验收；确实依赖用户账号/权限或不能恢复的外部条件才请求协助。
