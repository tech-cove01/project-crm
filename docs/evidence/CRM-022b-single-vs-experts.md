# CRM-022b 单 Agent 与三专家对照

2026-11-16，在独立 CRM 测试组织和真实 Pi 工作台上，以 DashScope `qwen3.8-flash` 成对执行。运行文件对应产品基线 `60f2ba577f9f113eadba6fa89d0c6d308dd04613`。每对固定同一销售 Agent、实际工具权限、合成业务字段、授权资料、温度配置、根任务 12 步和 36,000 token 规则。处理方式由 Workbench 的 `collaboration=disabled|auto` 区分。每轮为 inspect，单 Agent 可访问联系人、商机及同一授权 Wiki，三专家各按产品原有角色限制分工，运行总量包括父和子。原生预算在模型轮边界生效，费用未知。

正式任务计划为四类各三题，共 12 个案例。简单题各核对一个当前字段，跨来源题组合商机、客户和真实产品原文，冲突题以旧备注与当前 CRM 字段不一致来测试权威选择，缺证题要求保留实际 null，或核查检索为空。两份授权 Wiki 固定为一份 CSV 资料 v3 和一份内部阶段批准约定 v1，另用一个预检确认为空的词作对照。每类一题成对复跑，顺序与首轮交替。正式执行前按臂及重复轮次分配 32 个独立联系人和商机，复制对应的业务字段和说明，保留同一漏斗、阶段与资料。绑定对象 ID 和记录创建元数据各自独立，防止一臂产生的同商机持久复核阻断另一臂。独立校准另用一个商机。旧备注冲突是合成材料中的真值冲突，三专家间是否触发结构化复核以实际运行状态为准。

评分真值位于复核端。CRM 字段、终答和已观察的工具值必须一致。直接引用对应本次实际成功读取与结果文档中的 typed evidence。专家引用对应本 root 的实际 child 和该 child 的成功观察。政策摘录必须为授权页对应 ID、版本、正文哈希的原句，且含任务相关的正文锚点。缺失政策必须有同输入的正常空检索并留空。规则复核不调用 Judge。运行时根 Agent、scope、版本、budget、供应商和模型均单独比对。业务核对范围包含商机和联系人的精确 SQL 快照、活动数量、提案数量。

## 校准

单 Agent `6e016110-207c-43a4-9708-a287533f8a4d` completed，字段及支持引用均 3/3，23.30 秒，输入 10,421、输出 924，cache read 15,360。三专家 `226e385c-aff1-4f89-b72e-79a21e878452` 取得三条意图内子任务，两个 completed，政策专家检索未取到所需资料而 partial，父最终为 `collaboration_review_required`，未交付可评分的结构化终答。耗时 37.99 秒，输入 20,342、输出 3,133，cache read 28,160。两臂类别、状态及只读边界均得到实际验证。父运行后续试找到资料也未自动解除子任务留下的复核，消耗与失败原样保留。

第一次单 Agent 已创建且执行，采集 SQL 因列名不明确返回 `42702`。修复列别名后只凭同一已收到的 201 回执回读原 run，再完成唯一未执行的专家臂。两版冻结清单与失败保留在 `.local/crm022/paired/`。原任务、wiki 和对象快照、模型、步骤规则均相同。

补核并发配置。根任务 Worker 并发为 1。当前非 Mission 工作台允许同一父运行内最多 3 个专家并行，Mission 才将专家上限降到 1。本次校准三个 child 启动局限在 21 毫秒内且执行区间重叠，具体时间另存 `P01-specialist-timing.json`。对照使用实际总耗时和用量度量代价。

复现从 `node --env-file=.local/crm022/runtime.env scripts/eval/crm022-paired.mjs seed` 开始。核对两个授权 Wiki 页当前 ID、版本、正文 SHA-256 及缺证词确认为空，保存 `wiki-frozen.json`。先 `calibration`，核对两个执行布局及采集，再 `seed-twins` 固定正式对象，最后 `formal 12` 保存实测配置、目标和源文件哈希后逐项执行。每臂的意图、201 回执、可见终答、工具结果和逐项评分分开保留。发生采集故障时依据已收到的 201 读取原 Run，网络提交结果未知时先对账。正式用量预留和累计只决定后续请求是否开始，实际工作台仍使用本仓每轮预算规则。汇总使用 `node scripts/eval/crm022-paired-report.mjs`，校准与重复轮不计入首轮通过率。
