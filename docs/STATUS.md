### CRM-027 · 本体查询接入 Pi

1. 以“所选商机在指定 UTC 时间窗内有无已完成约见记录”为唯一模板。定义术语、版本、商机与活动关系及证据标准。只认 `crm_lead_activities.type = appointment_completed`，区分已经排期、取消和未到场。以 `performed_at` 匹配左闭右开区间。没有明确时间窗或所问指标尚未定义时要求澄清，查不到按“该时间窗内 CRM 无匹配记录”表达。查询异常、截断和空结果分别呈现。
2. 用白名单参数和固定参数化查询，明确时间窗与行数上限。执行时从持久 Run 取组织、所选商机及 `actor_user_id`，重查尚未撤销的组织 `manager`/`admin` 权限和当前对象可见性。`resolveWorkbenchScope` 只提供归属边界，读取权限须单独验证。工具入参仅接模板和时间窗，SQL 显式按组织、商机和窗口过滤。首版挂载于具备授权所选商机的 Workbench 父 Run，只返回活动 ID、类型和时间等所需字段。
3. 从当前 `createMissionQuestionTools` 的本地 ToolSet 挂载方式接入 Pi 开始/续跑，登记只读效果及可用工具。复用同 Run 的 `tool_completed`，由 `toolCallId` 关联口径版本、所选范围、时间窗、活动证据及结果状态，在现有运行详情展示。阶段引用和变更继续走既有工具、提案、人工确认及 Worker。本轮以工具回执和数据库核验活动来源，结构化引用沿用已有类型。代码入口见 `lib/leads/activity-vocabulary.ts`、`lib/agenda/laco.ts`、`lib/ai/agents/workbench-scope.ts`、`lib/ai/runtime/workbench-target-scope.ts`、`lib/ai/agents/workbench-start-job.ts`、`lib/ai/agents/run-resumed-workbench-turn.ts` 和 `lib/ai/agents/tool-effects.ts`。上游参照 ZIP 内 `lib/ontology/` 和 `docs/handoffs/HANDOFF-ontology-lite.md`。
4. **验收**：在独立库固定一个有完成活动的商机及事先写出的 SQL 预期，另造同客户其他商机/其他租户、取消活动、空窗口、缺口径和无权角色。用直接工具/SQL 校对正例和拒绝，无合法授权时活动数据不外泄且无业务写入。用一次真实 Pi `act` Run 执行“查到已完成约见后，才对所选商机提出指定阶段变更”，让建议依据关联同一次 `toolCallId` 及活动证据，确认回执实际可见于后续模型回合且刷新后可查。待批阶段不变，批准后仅一条实际变更回执，续跑用原工具回查且与 SQL 一致。`inspect` 写阻断和拒绝分支沿用原契约并做定向检查。若触及审批实现，再实走受影响分支。交付声明限于这个语义模板及已走通的受控执行链。

### CRM-028 · 客户记忆闭环

1. 在 `CustomerMemoryPanel` 加一个“从当前客户的历史单聊提取候选”入口和待审列表。使用现有联系人关联的单聊入口或明确选一条获准历史会话，限定已入站、未撤回的近期文本条数和长度。由现有 Gateway 作一次受限结构化提取，返回候选分类、正文、消息 ID 和短引文。服务器逐字核对引文及归属，只落候选；来源在获得授权时回读，数据库保存必要的来源标识与版本/摘要，控制正文副本。失败、无可提取信息、无权限分别展示。
2. 新候选表保存组织、联系人、来源、状态、决定人和确认事实 ID。有效 `manager`/`admin` 可确认、改写后确认或驳回。服务端校验角色和支持写权限，提交事务内重查成员权限、当前联系人和来源版本。确认时锁候选，抽出现有 `saveCustomerMemory` 共用的事务写入逻辑，同事务写候选决定、确认事实及现有 Mem0 outbox。按候选绑定稳定请求键，重放同决定回读原结果，冲突决定拒绝。待审内容只供授权人工查看。来源撤回时禁止晋升，联系人匿名化、合并或删除后的隔离和清理对齐现有 0406 隐私钩子。已确认内容使用现有撤回入口，沿用 50/10 召回、Mem0 投影和回退策略。
3. 入口见 `components/ai/CustomerMemoryPanel.tsx`、`app/api/v1/ai/customer-memory/route.ts`、`lib/ai/integrations/mem0.ts`、`lib/mcp/tools/contacts.ts`。结构化调用复用 `lib/agent-engine/edge/llm/run-model-call.ts`，可参照 `lib/ai/evals/semantic-judge.ts` 的内存提交工具。参考 ZIP 中 `lib/ai/customer-memory/{extraction,candidates}.ts` 及 `docs/specs/customer-memory-loop.md`。本仓已有 0409–0412，新增迁移前核对空号，同步 baseline 和 MANIFEST。
4. **验收**：用一条只在合成历史单聊出现的客户偏好，实际调用模型提取，确认前直接读取 SQL/Agent 工具无该事实、无 Mem0 同步事件。负责人在联系人页确认，同一决定重试/并发只产生一条确认记录及一个同步事件。验证驳回、来源撤回或变化、异客户、异租户、只读支持不可晋升。另起 `conversationId` 和 Run，问题不提示答案，不读原会话或旧 checkpoint，用真实 Pi 工具读回该事实，核对模型答复和 SQL 记录。最后用现有入口撤回，直接读取不再返回。自动触发、锁定/TTL、多轮模型刷新、召回更换和 RSI 留待另行选题。

最终报告最少记录：原始输入与预期的脱敏索引、实际 Run/提案/child/事件、工具观察及 SQL 事实/来源版本、成功/失败/unknown、模型与规则/Rubric 版本、实际调用和 tokens、指标分母、适用 SHA 与证据位置。历史原文和敏感材料只留本机；公开提交仅含脱敏摘要和复现说明。没有覆盖的保证明确列出，不从固定场景推导生产可用、整体准确率或所有路径安全。

### 迭代上限与停止条件

1. **首轮验证一次。** 动手前冻结上述有限场景及其预期，先复用可适用的证据，只补缺失的真实链路和分支。每个场景首次执行及失败均登记；同输入反复运行取最好答案、额外加题加角色或无限重建资料不在本批内。
2. **整批最多两轮缺陷修复。** 每轮开始先列首轮/上一轮证据确认的缺陷、原因假设与受影响场景，仅修已登记的接线、边界或正确性问题，一问题一提交；修后只复查受影响场景。同一缺陷最多两次修复尝试，仍未解决则结束该子项并保留失败/未知，不扩成框架重写。已有回归复跑标为已曝光，不再算新留出验证。
3. **最终独立核验一轮。** 固定最终干净源码 SHA，按场景组在独立自有数据/未用于调参的材料上复核关键结论，不重跑全部历史矩阵。新证据一旦用于修复就不再称盲测。Judge 每份选定材料只作一次评分；纯连接/解析失败最多一次有记录的技术重试，两次结果均保留，不因分数不够高重调。独立核验发现硬失败，停止对应主张的通过认定，不自动开启第三轮修复或新一批任务。
4. **立即停止有关写操作的条件。** 出现越权、错误对象变更、重复业务效果、不可解释的数据差异，或未知结果被盲重放时，先保存证据、停止该场景继续写入；在本批剩余修复额度内处理。到限仍失败，相关亮点标为待补或缩窄，不能带着错误状态宣称验收通过。不得随机停现有 Worker、操作其他项目服务、删除未知数据/卷或用真实客户渠道取证。
5. **两种合法终态。** 四条证据门槛全部通过，则本批完成、冻结并转简历/源码讲解/八股与算法；到达额度、缺少必要人工复核或仍有失败，则本批以受限结果结束，列清已通过/失败/blocked、已耗轮次及哪些表述不能使用，不把“结束”写成“全部实现”。恢复失败子项或新增场景须用户另行选择；云部署、自动记忆抽取/衰减和 RSI 均不自动进入下一轮。
