CRM 业务与实现详解

从一次销售跟进，理解 Agent 怎样取证、业务系统怎样授权，以及建议如何变成可核对的动作。

01 / A SALES FOLLOW-UP

从一句客户咨询，
到一次可核对的业务动作。

沿着赵强的年度服务合同，读懂完整 CRM 怎样调查、分析、等待人工决定，再核对执行结果。

业务教学场景 · 赵强的年度服务合同
“请再发一份年度合同，并确认预计什么时候开始。”

双方已沟通过服务范围，报价与交期仍未确认。销售希望系统先调查和分析；如果后续需要调整阶段，先形成具体提案交由人工决定。

谁在用，遇到什么问题？

销售团队和负责人准备跟进客户时，需要同时查看沟通记录、当前商机与产品条款。赵强问什么时候开始，但这笔商机的报价和交期仍未确认；只看一句咨询，销售无法直接作出承诺。

为什么需要 Agent？

每次咨询的问题和资料组合不同，Agent 适合理解目标、选择允许的工具、组织多来源建议。权限校验、字段更新和批准执行由确定性的业务代码负责，固定查询也可以直接交给普通接口。

  1. 01

    先确定：谁在跟进哪位客户、哪笔商机。

    销售选择赵强和这笔年度合同，提出复盘需求。系统先检查登录身份、组织、角色与对象关联，再保存一次任务记录（Run）。同一个客户可以有多笔商机，模型给出一个对象 ID 并不会自动获得操作权限。

    交付什么

    范围明确、可以查询状态的任务，以及本次需要核对的业务问题。

  2. 02

    把任务交给后台，让模型围绕工具调查。

    任务进入持久队列，独立 Worker 负责领取和执行。销售刷新页面后仍能查询保存的进度，长任务也可以等待人工决定。

    Pi 承接“调用模型 → 请求工具 → 接收结果 → 继续分析”的循环。CRM 业务层决定工具能读什么、能改什么；Worker 管后台执行，队列保存待处理工作，三者各有职责。

    交付什么

    可观察的调查过程与持久执行状态，后续审批和续跑有据可接。

  3. 03

    把客户想要什么，与公司能承诺什么分开查。

    先核对已确认的客户事实。SQL 保存当前正文，Mem0 辅助查找相关记忆、调整检索顺序；命中后仍回读 SQL，Mem0 不可用时已有确认事实也不会消失。

    服务范围和产品限制需要企业依据。WeKnora 帮助检索获授权资料，CRM 回读原文并核对来源版本。客户询问开始时间，不能据此推断公司已经承诺某个交期；资料没有覆盖的合同条款也要保留待核对。

    交付什么

    当前客户事实、可回查的产品依据，以及报价、交期等未确认项。

  4. 04

    分别取证，再形成一份商机判断。

    需要综合分析时，既定的三个只读专家分别核对客户事实、诊断商机、检查产品与政策，由父 Agent 汇总。专家提供证据和判断，不能各自修改商机；证据冲突、缺失或局部失败时保留复核状态。

    对赵强这笔合同，可以先明确：年度服务范围已经沟通过，报价与开始日期仍待客户确认。下一次跟进应围绕这些问题补充依据，不能把客户没有确认的内容写成已达成。

    交付什么

    带依据的下一步建议，清楚区分已知事实、分析判断与未确认项。

  5. 05

    如果要调整商机阶段，先让人决定具体动作。

    如果后续取证支持一项需要确认的阶段调整，CRM 先生成提案，绑定这笔商机、目标阶段和动作参数。提案待批准时，商机阶段尚未因此改变；有权限的人核对后明确批准或拒绝。

    批准只针对这项具体动作。拒绝后该提案不执行；部分可逆字段更新可以受控自动处理，不要求所有写入都走同一种人工审批。

    交付什么

    目标与参数明确的阶段提案，以及可追溯的批准或拒绝决定。

  6. 06

    执行后重新读取，再核对是否真正做好。

    获批动作由业务执行层核验并执行，保存回执，再安排续跑，重新读取商机实际状态，核对它是否与批准目标一致。执行结果未知时先暂停核对，不能直接重复操作。

    最后分开检查：任务是否结束、动作是否落在正确对象上、回答是否得到事实和引用支持。SQL 保存运行事实，Langfuse 帮助观察模型与工具过程；规则检查和按需语义复核分别判断质量。轨迹齐全不等于答案正确，阶段变化也不等于客户已经签约。

    交付什么

    实际商机状态、执行回执和回答相互对应的结果，以及后续仍需销售跟进的问题。

销售最终拿到的，是有依据的建议、明确的人工决定和可核对的动作结果。

模型结束、任务完成与客户成交，各自有不同的判断依据。

这里用赵强串起业务教学场景，解释完整 CRM 的实现。专家分析与阶段批准是不同任务，不表示同一个 Run 自动完成整条销售流程。

03 / CORE CAPABILITIES

项目的四条核心能力。

模型提供理解与推理，业务系统负责事实、权限和动作。四条主线共同支撑从分析建议到销售协作的过程。

A / PI AGENT CORE↗

Pi 内核与受控执行

以开源 Pi Agent Core 为执行内核，适配 CRM 工具、事件和运行消息。Pi 管模型/工具循环，CRM 业务 Harness 管权限和副作用，Worker 管任务领取与状态推进。

Pi 循环↔业务约束↔Worker 调度
  • 循环适配与收口：通过模型网关和 MCP 工具接入；轮次与预算参与停止判断，末轮只开放结构化结果提交
  • 持久执行：SQL 队列与租约承接长任务，保存 Pi 消息及事件，为审批后续跑提供依据
  • 授权后续跑：恢复时重新装配当前业务约束，执行后保存回执、重读结果；未知结果先暂停核对
B / CONTEXT◎

客户记忆与可信知识

客户确认事实与企业产品依据分别管理。记忆检索帮助找信息，SQL 和授权原文决定最终能使用什么。

客户这边偏好 · 事实 · 约束SQL 权威正文 / Mem0 辅助检索
企业这边产品 · 政策 · FAQ原生 RAG / WeKnora 来源回读
  • 事实重新核对：命中后校验归属，重读当前正文
  • 不可用时回退：外部记忆服务失败，仍能读取本地事实
  • 资料更新后复核：改版或撤回后，旧依据重新核验
C / MULTI-AGENT✳

多 Agent 协作与商机分析

三类专家各自建立持久子任务，运行独立 Pi 循环，以结构化结果交给父 Agent 汇总。协作采用固定计划，专家只读，受控写入由父流程接回 CRM。

客户事实商机诊断政策顾问
↘父 Agent 汇总建议↙
  • 角色与执行边界：每个专家有工具白名单、对象和知识范围，以及轮次、工具调用和模型预算约束
  • 结构化证据对照：比较字段值与来源版本，区分真实分歧、资料变化和互补信息
  • 失败与冲突处理：保留缺证、超时和局部失败；权威重读后仍未解决的冲突进入持久人工复核，并阻断相关动作
D / EVALUATION⌁

Agent 观测与评测回归

任务跑完不代表动作正确，动作正确也不等于回答可靠。运行事实、规则检查和语义复核分别保留。

任务完成运行状态
动作正确工具与回执
回答可靠引用与语义
  • 运行与观测解耦：SQL 保存事实，脱敏轨迹异步投递 Langfuse；投递重试不重复执行业务
  • 规则与语义分层：规则核对字段与引用，Judge 按需复核，合并时保留更严格结论
  • 失败进入回归：实际误述、错引与无答案误召回保留为样本，支持后续策略复查

05 / DESIGN CHOICES

为什么这样设计？

把销售场景里的约束转化为明确的工程选择。

01

长任务离开请求生命周期

商机分析可能调用多个工具，也可能等待人批准。独立 Worker 与持久队列保存过程，让页面交互与后台执行各自推进。

请求返回之后，任务仍有状态可查。
02

事实与检索结果各司其职

检索擅长从大量信息中发现候选；业务需要当前、授权、可解释的依据。SQL 保存确认事实，外部记忆辅助排序，知识引用回读原文。

找到信息之后，还要确认它能否使用。
03

建议与执行分别负责

专家各自取证，父 Agent 汇总建议；权限与审批由业务层执行。需要确认的动作绑定明确目标，未知结果保留核对入口。

有分析能力，也有可解释的决定过程。
