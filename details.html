CRM 业务与实现详解

销售可以按统一口径筛查商机，把历史聊天中的客户偏好核实后带入新会话，再参考授权资料准备跟进。需要调整阶段时，负责人先核对依据并批准，执行后回查商机的实际阶段。

01 / A SALES FOLLOW-UP

从一句客户咨询，
到一次可核对的业务动作。

沿着赵强的年度服务合同，读懂完整 CRM 怎样调查、分析、等待人工决定，再核对执行结果。

业务教学场景 · 赵强的年度服务合同
“请再发一份年度合同，并确认预计什么时候开始。”

双方已沟通过服务范围，报价与交期仍未确认。销售希望系统先调查和分析；如果后续需要调整阶段，先形成具体提案交由人工决定。

谁在用，遇到什么问题？

销售团队和负责人准备跟进客户时，需要同时查看沟通记录、当前商机与产品条款。示例客户赵强问什么时候开始，但这笔商机的报价和交期仍待确认，销售需要先核对依据。

为什么需要 Agent？

每次咨询的问题和资料组合不同，Agent 适合理解目标、选择允许的工具、组织多来源建议。权限校验、字段更新和批准执行由确定性的业务代码负责，固定查询也可以直接交给普通接口。

  1. 01

    先确定：谁在跟进哪位客户、哪笔商机。

    销售选择赵强和这笔年度合同，提出复盘需求。系统先检查登录身份、组织、角色与对象关联，再保存一次任务记录（Run）。同一个客户可以有多笔商机，模型给出一个对象 ID 并不会自动获得操作权限。

    交付什么

    范围明确、可以查询状态的任务，以及本次需要核对的业务问题。

  2. 02

    把任务交给后台，让模型围绕工具调查。

    任务进入持久队列，由独立 Worker 领取。销售刷新页面仍能查询进度，长任务可以等待人工决定。

    Pi 承接调用模型、请求工具和读取结果的循环。查询商机或约见时，CRM 工具按审核目录判断哪些口径可用，并核对授权范围。看商机筛查与口径说明

    交付什么

    可回查的取证和持久执行状态，后续审批与续跑都有记录。

  3. 03

    把客户想要什么，与公司能承诺什么分开查。

    销售可以从授权单聊提取记忆候选，核对客户原文后确认。新会话读取 SQL 的当前事实，Mem0 可辅助排序。看记忆提取与确认步骤

    服务范围和产品限制需要企业依据。WeKnora 帮助检索获授权资料，CRM 回读原文并核对来源版本。客户询问开始时间，不能据此推断公司已经承诺某个交期；资料没有覆盖的合同条款也要保留待核对。

    交付什么

    当前客户事实、可回查的产品依据，以及报价、交期等未确认项。

  4. 04

    分别取证，再形成一份商机判断。

    需要综合分析时，既定的三个只读专家分别核对客户事实、诊断商机、检查产品与政策，由父 Agent 汇总。专家提供证据和判断，不能各自修改商机；证据冲突、缺失或局部失败时保留复核状态。

    对赵强这笔合同，可以先明确：年度服务范围已经沟通过，报价与开始日期仍待客户确认。下一次跟进应围绕这些问题补充依据，不能把客户没有确认的内容写成已达成。

    交付什么

    带依据的下一步建议，清楚区分已知事实、分析判断与未确认项。

  5. 05

    如果要调整商机阶段，先让人决定具体动作。

    如果后续取证支持一项需要确认的阶段调整，CRM 先生成提案，绑定这笔商机、目标阶段和动作参数。提案待批准时，商机阶段尚未因此改变；有权限的人核对后明确批准或拒绝。

    批准只针对这项具体动作。拒绝后该提案不执行；部分可逆字段更新可以受控自动处理，不要求所有写入都走同一种人工审批。

    交付什么

    目标与参数明确的阶段提案，以及可追溯的批准或拒绝决定。

  6. 06

    执行后重新读取，再核对是否真正做好。

    获批动作由业务执行层核验并执行，保存回执，再安排续跑，重新读取商机实际状态，核对它是否与批准目标一致。执行结果未知时先暂停核对，不能直接重复操作。

    最后分开检查：任务是否结束、动作是否落在正确对象上、回答是否得到事实和引用支持。SQL 保存运行事实，Langfuse 帮助观察模型与工具过程；规则检查和按需语义复核分别判断质量。轨迹齐全不等于答案正确，阶段变化也不等于客户已经签约。

    交付什么

    实际商机状态、执行回执和回答相互对应的结果，以及后续仍需销售跟进的问题。

销售最终拿到的，是有依据的建议、明确的人工决定和可核对的动作结果。

模型结束、任务完成与客户成交，各自有不同的判断依据。

这里用赵强串起业务教学场景，解释完整 CRM 的实现。专家分析与阶段批准是不同任务，不表示同一个 Run 自动完成整条销售流程。

按统一口径筛查商机

业务本体（Ontology Lite）把商机、活动和两者的关系写入版本化目录。销售可以问「哪些商机还开放」，再按相同口径缩小跟进范围。

已验收案例讲解，不连接实时模型或数据库

  1. 在工作台选定销售漏斗

    在本地应用打开「Agent 工作台」，进入「任务设置」。在 CRM 对象类型选「销售漏斗」，搜索并选中合成管道。返回输入区，将执行模式设为「只读检查」。

    预期 任务设置中显示所选目标。查询仍需通过服务端的组织和角色检查。

  2. 先查开放商机，再按约见记录筛查

    输入「当前授权范围内的开放商机」，点「运行 Agent」。再问「当前授权范围内在 2026-11-10T09:00:00Z 到 2026-11-10T12:00:00Z 内没有已完成约见记录的开放商机」。

    预期 合成案例在未归档漏斗中返回 3 条当前状态为开放的商机，其中 1 条在指定 UTC 时间窗内没有已完成约见记录。窗口包含起点、排除终点，排期和取消均不计为完成。缺少 CRM 记录无法证明客户没被跟进。

  3. 查看依据，遇到缺定义先澄清

    打开「运行详情」，在「执行时间线」找「业务语义回执」，查看口径版本、范围、时间窗和记录。也可以只读询问「在授权范围内，哪些开放商机是高潜但跟进不足？」

    预期 Agent 说明需要高潜判据和有效跟进的渠道、要求与时限，保留已知范围并暂停该查询。

  4. 对一笔商机取证，再由负责人决定

    另起任务，在「任务设置」选择一笔合成「商机」，切到「分级自治」。要求只在指定 UTC 窗口查到已完成约见时，才对该商机提出指定阶段变更。组合筛查结果不具备直接改阶段的资格。

    预期 提案带约见记录和取证调用 ID，待批时阶段保持原值。有权限的负责人在「运行详情」核对后选择「批准执行」或拒绝。

  5. 对照执行回执与实际阶段

    批准后由 Worker 执行。在「运行详情」核对唯一的执行回执，刷新后在时间线回查续跑读取的商机阶段。拒绝则对照原阶段。

    预期 获批案例中的商机阶段符合批准目标。可以继续通过下面的静态模拟体验两条路径。

让确认过的客户偏好随新会话复用

客户在历史单聊中既提到沟通偏好，也提到一个回访时间。负责人只确认偏好，新会话便能区分已确认事实和仍待审的候选。

已验收案例讲解，不连接实时模型或数据库

  1. 打开联系人，确认有授权历史单聊

    在本地应用的「联系人」打开合成客户档案，找到「客户记忆」下的「待审记忆候选」。界面会使用该联系人可访问的一个历史单聊，并显示提取入口。群聊、撤回文本和其他客户的消息不会作为该次来源。

    预期 有可用单聊时可以开始提取。若显示「没有可用的历史单聊」，先为该联系人准备合规的合成入站消息。

  2. 提取候选，逐条看客户原文

    点击「从历史单聊提取候选」，在候选下查看「客户原文」。这次合成单聊中写道：“回访前先发一条标题含「蓝杉窗口」的中文消息，这是我的固定沟通偏好。”另有一条候选提到周二 16:40。

    预期 偏好和时间分别列在待审区，服务器核对引文与消息归属。此时两条都不能被 Agent 作为确认事实读到。

  3. 只确认沟通偏好，时间留待审核

    负责人检查原文，点偏好旁的「确认候选」。无效候选可点「驳回候选」。来源消息修改或撤回后，旧候选无法确认。

    预期 沟通偏好进入 SQL 记忆，回访时间仍留在待审区。同一候选重复或并发确认只生成 1 条事实和 1 条同步事件。

  4. 另开新对话，让 Agent 回读确认事实

    在「Agent 工作台」点「新对话」，在「任务设置」核对选中的是同一个联系人。以「只读检查」询问「技术回访是什么时间？开始前偏好收到怎样的信息？」

    预期 Agent 从确认记忆读出「蓝杉窗口」的中文消息偏好，说明尚无已确认的回访时间。

  5. 撤回后再问，核对偏好不再召回

    返回联系人档案的「客户记忆」，对该条确认事实点击「删除此记忆」。在新会话重复只读查询。

    预期 页面提示已停止使用，后续读取不再返回被撤回的事实。需要更新时，先撤回旧事实，再确认新事实。

05 / DESIGN CHOICES

为什么这样设计？

把销售场景里的约束转化为明确的工程选择。

01

长任务离开请求生命周期

商机分析可能调用多个工具，也可能等待人批准。独立 Worker 与持久队列保存过程，让页面交互与后台执行各自推进。

请求返回之后，任务仍有状态可查。
02

事实与检索结果各司其职

检索擅长从大量信息中发现候选；业务需要当前、授权、可解释的依据。SQL 保存确认事实，外部记忆辅助排序，知识引用回读原文。

找到信息之后，还要确认它能否使用。
03

建议与执行分别负责

专家各自取证，父 Agent 汇总建议；权限与审批由业务层执行。需要确认的动作绑定明确目标，未知结果保留核对入口。

有分析能力，也有可解释的决定过程。
